## Decisions and assumptions

1. **Table names** match the spec exactly: `users`, `recipes`, `recipe_components`, `cutting_orders`, `verification_items`, `verification_logs`. Use `@@map` for table names and `@map` for columns so the database uses snake_case while Prisma models use PascalCase and camelCase.
2. **Ids** are integer autoincrement. `order_no` is a separate unique string (for example `CUT-0001`), generated by the server later.
3. **Enums:**
   - `Role`: `cutting_supervisor`, `cutting_verifier`, `sewing_supervisor`
   - `OrderStatus`: `CUTTING_IN_PROGRESS`, `PENDING_VERIFICATION`, `REJECTED`, `VERIFIED`, `IN_SEWING`
   - `ItemStatus`: `GREEN`, `YELLOW`, `RED`
   - `Decision`: `APPROVED`, `REJECTED`
4. **Uncounted components:** `verification_items.actual_qty` and `verification_items.status` are nullable. `NULL` means the Verifier has not counted that component yet. This is how the server detects "missing or uncounted" (spec section 9). Item rows are created when the order is submitted, one per recipe component, with `expected_qty` filled in.
5. **Money style numbers use Decimal:** `std_fabric_yards` Decimal(6,2), `wastage_cap` Decimal(5,2), `actual_fabric_yds` Decimal(8,2), `wastage_pct` Decimal(6,2).
6. **Audit snapshot:** `verification_logs` gets an extra `variances` JSON column holding the per component expected, actual, variance, and status at decision time. The spec requires variances to be stored permanently. The snapshot keeps them even if item rows are later reset on resubmission.
7. **No extra columns on `cutting_orders`.** It has only the columns the spec lists. The `IN_SEWING` status covers the Start Sewing action. The only addition beyond the spec's minimum schema is `verification_logs.variances` (assumption 6).
8. **No cascade deletes.** All foreign keys use `Restrict`. Audit data must not disappear because a parent row was deleted.
9. **Email** is unique and stored lowercase (the server lowercases it).

## Requirements

**Models and relations** follow spec section 8:

- `users`: id, email (unique), password_hash, role, full_name, created_at
- `recipes`: id, recipe_code (unique), name, category, std_fabric_yards, wastage_cap
- `recipe_components`: id, recipe_id, component_name, pieces_per_garment, image_url (nullable); belongs to recipe
- `cutting_orders`: id, order_no (unique), recipe_id, target_qty, fabric_roll_id, actual_fabric_yds, status (default `CUTTING_IN_PROGRESS`), created_by, created_at, updated_at
- `verification_items`: id, order_id, component_id, expected_qty, actual_qty (nullable), status (nullable); unique on (order_id, component_id)
- `verification_logs`: id, order_id, verifier_id, decision, rejection_note (nullable), wastage_pct (nullable), variances (JSON), timestamp (default now)

**Indexes:** `cutting_orders(status)`, `cutting_orders(created_by)`, `verification_items(order_id)`, `verification_logs(order_id)`.

**Hand written SQL appended to the generated migration** (use `prisma migrate dev --create-only --name init`, edit the file, then apply):

- CHECK `cutting_orders.target_qty > 0`
- CHECK `cutting_orders.actual_fabric_yds > 0`
- CHECK `recipe_components.pieces_per_garment > 0`
- CHECK `verification_items.expected_qty > 0`
- CHECK `verification_items.actual_qty IS NULL OR verification_items.actual_qty >= 0`
- CHECK on `verification_logs`: if `decision = 'REJECTED'` then `rejection_note` is not null and `length(trim(rejection_note)) >= 5`; if `decision = 'APPROVED'` then `wastage_pct` is not null
- Trigger that raises an error on any UPDATE or DELETE on `verification_logs`
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on all six tables, with no policies

## Security considerations

- The Supabase Data API is off for this project, and RLS is enabled as a second layer, so `users.password_hash` is not reachable through any public API.
- The audit table cannot be edited at the database level, not only in application code.
- No connection strings or passwords go into the schema, the migration, or any committed file.

## Acceptance criteria

1. `npx prisma validate` passes.
2. `npx prisma migrate status` reports the database is up to date.
3. Supabase Table Editor shows exactly the six tables, each marked with RLS enabled.
4. In the Supabase SQL editor, each of these fails with a constraint or trigger error:
   - inserting a `cutting_orders` row with `target_qty = 0`
   - inserting a `verification_items` row with `actual_qty = -1`
   - inserting a REJECTED `verification_logs` row with an empty note
   - updating or deleting any `verification_logs` row
5. `npx prisma generate` succeeds and `/api/health` still returns ok.
6. `schema.prisma` has no `url` in the datasource block.
